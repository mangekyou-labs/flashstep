# The settle bot — issue #11

The CLI watches `UpDownRounds` and `ThresholdPots`, captures their pinned Readings and calls permissionless `settle(roundId)`. It never opens a Player position, claims, withdraws, funds a Campaign or changes settings. Its dedicated wallet needs ETH for gas and no contract role. It works with ETH or ERC-20 stakes because the bot never transfers the stake asset.

## Run during a pilot or after handover

Install this repo's dependencies with `yarn install` and compile the matching contracts with `yarn foundry:compile`. Keep the resulting `packages/foundry/out/UpDownRounds.sol/UpDownRounds.json` and `ThresholdPots.sol/ThresholdPots.json` alongside the script; the CLI reads their ABIs. Use Node 20.18.3 or later and the existing Foundry workspace dependencies. Supply the following environment variables to the process, then run `yarn settle:bot` from the repository root. No account/deployment command is run by the bot.

| Variable                     | Meaning                                                                                             | Default   |
| ---------------------------- | --------------------------------------------------------------------------------------------------- | --------- |
| `SETTLE_RPC_URL`             | HTTP(S) RPC for the contracts' chain; required                                                      | none      |
| `SETTLE_PRIVATE_KEY`         | Dedicated, gas-funded bot wallet's private key; required                                            | none      |
| `SETTLE_UPDOWN_ADDRESS`      | Deployed `UpDownRounds`; required                                                                   | none      |
| `SETTLE_THRESHOLD_ADDRESS`   | Deployed `ThresholdPots`; required                                                                  | none      |
| `SETTLE_FROM_BLOCK`          | Earliest deployment block of either contract; must include all `RoundSeeded` events                 | `0`       |
| `SETTLE_REQUEST_INTERVAL_MS` | Minimum wait after each RPC response before starting the next request                               | `10`      |
| `SETTLE_BLOCK_TIME_MS`       | Canonical cadence: `200` or `2000`; inferred from adjacent whole-second timestamps when omitted       | inferred  |
| `SETTLE_POLL_MS`             | Delay between polling passes                                                                        | `50`      |
| `SETTLE_LOG_BLOCK_RANGE`     | Maximum historical block range requested per contract per pass                                      | `2000`    |
| `SETTLE_GAS_LIMIT`           | Explicit transaction gas ceiling, including captures that cannot be estimated before their boundary | `1500000` |

Supply secrets through the process environment or your service manager's secret store. The script does not load `.env` automatically. Run one instance per wallet, and give it a key separate from the payer/owner wallet and other transaction senders. RPC responses, URLs and private keys are never included in its JSON logs. `SIGINT`/`SIGTERM` finishes the current bounded RPC operation and stops polling; it does not cancel transactions already submitted.

The request interval covers reads, log scans, simulation, broadcasting and receipt checks. The default allows at most roughly 100 RPC requests/second before network latency; increasing it lowers that ceiling and can make exact boundaries impossible to catch. Set the polling and request intervals to suit the provider and monitor actual successful captures. This setting is a ceiling on request rate, not a promise of two-second liveness.

On native 200ms chains, the bot checks known deadlines between background RPC requests. Three seconds before the earliest known boundary it checks pending capture receipts, then pauses discovery, historical replay and settlements, refreshes both contracts’ schedules and known uncached Rounds, rechecks the relevant Rounds, obtains gas/nonce data and signs the capture group. With valid native `timestampMs` metadata, it polls until the final 200ms block before the target second, then broadcasts prepared transactions in nonce order with a fresh phase check before each broadcast. Valid heads lie in `[boundary*1000−200, boundary*1000+800)`; the final block of the target second is too late. Metadata must agree with the whole-second timestamp and native cadence. If optional metadata is absent, it falls back to the less precise whole-second check; `ready.nativeTimestampMs` exposes that limitation. No wall-clock estimate decides when to submit: the host clock only determines when to pause maintenance. Nonce allocation through broadcast is a critical section, so a capture cannot reuse the nonce of an already-signed settlement.

Use a low-latency dedicated RPC. Even with preparation, every capture must be included before the target second ends; a group can require three sequential broadcasts. Startup, network latency, transaction inclusion and node stalls can still miss this window. Increasing polling/request delays reduces the available margin. The CLI preserves exact Reading semantics and never uses a later price as a replacement.

Base's [throughput and limits documentation](https://docs.base.org/specifications/transactions/throughput-and-limits) identifies the public mainnet and Sepolia endpoints as rate limited and unsuitable for production systems. It publishes no universal numeric requests-per-second allowance. Use a dedicated provider for a live Campaign, follow that provider's current plan limits and decrease `SETTLE_LOG_BLOCK_RANGE` if its log-query limits demand it. A public endpoint is suitable for an initial connectivity check, not an assurance that these deadlines will be met. Base's [Denim specification](https://docs.base.org/upgrades/denim/200ms-blocks) documents native 200ms blocks, live on Base Sepolia since October 21, 2026. Five canonical blocks share each EVM timestamp second. These are complete blocks, rather than the earlier Flashblocks preconfirmations. Explicitly set `SETTLE_BLOCK_TIME_MS=200` for that network; the override is also useful for local fixtures whose initial adjacent blocks do not represent their intended mining cadence.

## Captures, settlement and recovery

Up/down requires `captureBoundary` at both the exact trading cutoff and the exact Window end; threshold requires it at the Window end. Calling `settle` late without captures cannot recreate those prices. On native 200ms chains it prepares ahead and uses the millisecond phase guard described above. On legacy two-second chains it retains the one-block-ahead submission rule (`latest.timestamp + 2 === boundary`). Both use explicit gas limits because simulating a capture before its boundary would be too early. Both contracts can capture the same reader in one block; each Round still needs its own pointer transaction. The contracts' timing granularity validation remains unchanged: their trading/window durations are still even seconds. The reader already pins by actual block number and timestamp, so this bot fix requires no contract redeployment.

Transaction inclusion, RPC latency, a missing pool observation or an unexpected block cadence can make a capture fail or miss its target. The bot cannot guarantee inclusion in that exact next block and cannot safely substitute a later price. Such Rounds follow the existing contract rules: retry settlement, finalize eligible outage refunds after the 60-second Reading grace period, and finalize the 24-hour unsettled expiry. Market-cap threshold Readings also require settlement in a later block than the captured end block. Simulation naturally defers that call until it succeeds.

The bot rechecks stored `round.result` and simulates settlement before sending. A Round already settled when checked spends no gas. Another sender can still settle between simulation and inclusion; no offchain bot can eliminate that competing-transaction race. `phase()==Refunded` alone is not a stored settlement, so the bot still finalizes an eligible refund when `round.result` is zero.

Discovery combines the current scheduled Round with a recent `RoundSeeded` log scan before captures, plus a chunked historical replay from `SETTLE_FROM_BLOCK`. The recent scan searches backward using actual block timestamps until it covers at least 64 seconds (or reaches `SETTLE_FROM_BLOCK`), rather than assuming 32 blocks represent 64 seconds. This also captures an older Round when a newer Round is current. The recent cursor is clamped to that elapsed-time lookback after downtime, including after RPC downtime, and each query respects `SETTLE_LOG_BLOCK_RANGE`. Historical replay runs after captures. Unmaterialized historical schedule slots hold no escrow and are left alone. Captures take priority over the bounded rotating historical settlement queue. No local file is authoritative: restarting replays the chain and finds old escrow even after a Campaign stops and `currentRound()` returns zero. Starting from too late a block can hide old unsettled escrow. Large backlogs take multiple full blocks to scan.

The bot tracks signed transaction hashes and nonces until receipts arrive. On restart it waits for an existing wallet queue to drain before sending fresh work. An uncertain broadcast is checked against receipts, the sender nonce and transaction lookup; after three absent-block observations it may rebroadcast the identical signed settlement, whose nonce prevents duplicate execution. An absent expired capture without higher locally pending nonces is removed instead of being rebroadcast too late. Locally pending nonces remain reserved even if the provider has not exposed them yet. Uncertain acceptance pauses new sends until reconciliation. Every capture retry checks a fresh head inside the wallet critical section. If an expired absent capture has higher locally pending nonces behind it, the bot retains it, logs `nonce_gap` and pauses fresh work until receipt/nonce reconciliation or manual wallet recovery resolves the queue. Known RPC rejections clear their pending entry for future retry unless higher locally pending nonces depend on it; those queues also pause for reconciliation. A transaction still present in the provider's mempool is left pending; the CLI does not cancel or replace it. If the wallet queue remains stuck, inspect that wallet's pending transactions with the provider, resolve the stuck transaction and restart. A restart cannot remove a pending transaction from the chain's mempool.

An observed capture revert stops fresh sends with exit status 1 and `capture_failed`. When possible, a historical read-only call decodes the revert reason. This does not cancel transactions already broadcast. Inspect the receipt and diagnostics before restarting. Submitted capture logs include the checked head, head request duration and broadcast duration.

Before a paid rehearsal, run `node scripts-js/rpcTiming.js` from `packages/foundry` with only `SETTLE_RPC_URL` set. It samples 12 latest blocks without a wallet or transactions and reports request latency, `timestampMs` availability and approximate head age. Head age includes local clock skew; these reads cannot predict transaction inclusion. Output omits the URL.

JSON events include `ready`, `submitted`, `confirmed`, `reverted`, `broadcast_rejected`, `broadcast_uncertain`, `capture_prepared`, `missed_boundary`, `nonce_gap` and `retry`. Inspect transaction hashes on the configured chain and watch for persistent retries or absent successful captures. RPC failures retry at the configured pace without terminating the long-running process. Use the same deployment block and addresses after restarting.

## Local smoke verification

Run `yarn settle:bot:smoke`, or from `packages/foundry` run `forge build` then `node scripts-js/settleBot.smoke.js`. The smoke script spawns its own isolated Anvil on a local port, deploys both real Round contracts with `BasePoolReader` and the existing deterministic pool/token mocks, and uses a separate unprivileged Anvil wallet for the actual CLI child process. It adds no JS test runner.

The smoke checks successful UpDown Tie and threshold Yes settlement without Player settlement; a process restart exactly one block before an older Round’s end while a newer Round is current; another restart while capture transactions are pending; historical recovery; a different wallet skipping already-settled Rounds with its nonce still zero; configurable RPC use through a local forwarding server; observed default request pacing with no interval/poll overrides and a separate explicit 20ms override; and rejection of an invalid request interval. It asserts actual stored results, not just phases or log messages. Anvil timestamps advance explicitly in two-second blocks, so this demonstrates correct scheduling under controlled inclusion, not production network reliability.

Red/green evidence: the first on-chain smoke failed because `settleBot.js` did not exist, then passed with the CLI. The request-pacing assertion initially failed when spacing was measured from request start, because initial connection latency compressed server-observed arrivals. Waiting after response completion fixed the failure. No Solidity contract, generated deployment manifest or challenge test is changed by this ticket.

Review regression evidence: restarting at end-minus-two seconds with a newer current Round originally failed to queue the older end captures. Scanning recent events and promoting their unfinished ids before the capture pass makes that exact CLI regression pass.

## Native 200ms regression — issue #39

The smoke command also runs `settleBot.denim.smoke.js` for restart recovery, with `--overlap`, and with `--late`. The real CLI signs only with a public Anvil test account, against isolated local Solidity deployments. The fixture mines five blocks per timestamp second at roughly 200ms wall-clock intervals and adds 60ms to every bot RPC response. Its forwarding proxy supplies controlled `timestampMs` values matching each manually mined block.

The original bot failed the native cutoff assertion. The fixed bot detects 200ms cadence, captures and settles UpDown as Tie and threshold as Yes, and recovers a stopped Campaign whose seed is more than 32 blocks old. The overlap run requires three simultaneous captures and verifies three stored normal results per contract with no reverted transactions. These tests establish behavior under the controlled fixture; live Sepolia inclusion remains an owner-operated QA gate.

The `--late` case delays a real signed capture until after its boundary, mines the actual revert and verifies that the CLI stops with decoded `OutsideBoundary` after one submission.

Twelve focused recovery and phase regressions cover local nonce reservation, uncertain acceptance after cross-contract discovery, definite rejection, fresh timestamp guards during retries and simultaneous captures, legacy timing, and expired/rejected lower-nonce queue gaps. Run them alone with `node --test scripts-js/boundaryScheduler.test.js scripts-js/captureWindow.test.js` from `packages/foundry`.
